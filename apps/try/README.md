# try.wakeshift.ai

A webhook URL that wakes your agent: get a link, add it to your agent (Claude Code, Codex, Cursor, Antigravity, opencode, Copilot CLI or any MCP client), ask the agent to watch, and every POST to your webhook URL (curl, Postman, GitHub, your own app) wakes it. A dev tool with low limits, and the first real user of the TypeScript SDK (`sdk/typescript`, `@wakeshift/sdk`).

## How it works

- **Stateless links.** A link's code is signed with `TRY_SECRET` and names a random webhook ID and when it was made. The MCP URL (`/t/<code>/mcp`), the page (`/l/<code>`), the webhook URLs (`/in/<token>`, one token per signature check) and the signing secret are all derived from it. Nothing is stored. A link expires after 7 days without use; when it was last used is kept in the database (written at most every 5 minutes per instance). When it expires, Wakeshift is asked to forget the webhook (`forgetUser` with the webhook ID, which is the app's user for it): its workspace, the conversations that watched it, their subscriptions and deliveries. The sweep queues it in the database in the transaction that deletes the link's own rows, and every instance works the queue every 10 minutes, retrying a failure with backoff (a minute, doubling, at most 6 hours) until Wakeshift says it's done.
- **The SDK user is the webhook; posts are an event.** `webhook.received` (argument: the webhook's ID; only the webhook's own SDK user, anyone with its link, may subscribe) carries what was posted: `summary`, a line saying what happened, then the parsed body, the headers that say who sent it, and `check`, the URL it came to (`open`, `github`, `stripe`, `linear` or `bearer`), so the agent can tell a verified post from one anyone with the open URL could send; the event's description and `webhook_info` say so. Every tool is registered with `attached.registerTool` (on the handle `wake.attach` returns), which adds Wakeshift's arguments to it in tools/list; only `watch` declares `subscribes: [webhook.received]`. Because the event has `authorize`, `subscribe_events` and native MCP Events clients may subscribe to it too, and only the webhook's own user is allowed. `watch` subscribes the calling conversation with `call.subscribe`; `unwatch` ends it with `call.unsubscribe`. The wrapper adds one Wakeshift block to each tool's result: how the conversation is woken after a subscribe, pending messages and a Codex thread's beacon otherwise. A call that fails ends the subscription it made. A client that speaks MCP Events (ChatGPT) gets no conversation subscription: the block tells it to subscribe to `webhook.received` itself. A post becomes `event.emit`. `wake.attach` adds `subscribe_events`, `unsubscribe_events` and `list_subscriptions`.
- **MCP:** Streamable HTTP with sessions, no sign-in (the code in the URL is the credential). Nothing about a session lives in an instance: initialize's client name, version and capabilities are stored under the `Mcp-Session-Id`, and each request builds the MCP server afresh from them on whichever instance it reaches (the SDK's transport in stateless mode; the session ID is checked here, 404 if unknown or another link's). So sessions survive restarts and need no affinity, and the client's name and capabilities (which decide how Cursor, opencode and the rest are woken, and whether a client subscribes itself) are right on every instance: the rebuilt server answers `getClientCapabilities` from the stored initialize, and passes the stored client name to the wrapper through `attach`'s `identify`. Sessions idle for 7 days are dropped (the client initializes again). A protocol 2026-07-28 request (OpenClaw's MCP Events client speaks nothing older) has no session: it's served as it comes, its client and capabilities from its own `_meta`, and the SDK's `attach` answers its `server/discover`. Tools: `watch`, `unwatch`, `recent_posts`, `webhook_info`.
- **Webhooks:** `POST`, `PUT` or `PATCH` `/in/<token>`, any body up to 64 KB. The event's `text` says what happened. A service's line is only for a post that passed its signature check, on its own URL: on the GitHub URL (from `X-GitHub-Event`) `GitHub workflow_run completed: failure on main (tests) in acme/api`; on the Stripe URL `Stripe invoice.payment_failed: in_…, USD 49.00, open (evt_…, test mode)`; on the Linear URL `Linear Issue create: ENG-123 Checkout page 500s`. Anyone with the open URL can send GitHub's, Stripe's or Linear's headers and body, so a post there is `Unverified POST to your webhook (open URL)` whatever it claims, and one to the bearer URL (or a GitHub URL post without `X-GitHub-Event`) says what was checked: `POST to your webhook (bearer token checked)` (each with `, empty body` in the parentheses if it was). The data has the rest: the text doesn't repeat the body, so a small post's data fits on one Monitor line (480 bytes) in full. Its `data` is the parsed body (`body`, or `body_base64`), the method, content type, a few headers that say who sent it (including `Linear-Event` and `Linear-Delivery`; never Authorization, cookies or signatures), `check` (the URL's check) and, on the Stripe and Linear URLs, `source` (the event type and ID). Retries are one publish, by an ID that only what the URL checks can set. On the GitHub and Linear URLs it's the SHA-256 of the signed body (Linear's without `webhookTimestamp`, which Linear sets anew for each try): their delivery headers and `Idempotency-Key` aren't signed, so a captured delivery replayed with fresh ones is still the same publish. On the Stripe URL it's the `evt_` ID from the signed body. Wakeshift dedupes an ID for a day; the same ID with another payload (a replay's other headers, Linear's new timestamp) is refused by Wakeshift as `id_reused`, which these URLs answer as a duplicate (202, `duplicate: true`). GitHub's signature has no timestamp, so a delivery replayed more than a day later wakes the agent again. On the open and bearer URLs whoever may post sets the headers anyway: `Idempotency-Key`, else `X-GitHub-Delivery`, `Linear-Delivery` or a Stripe event's `evt_` ID. `GET` explains how to post; a body more than 256 KB over the limit has its connection dropped rather than read.
- **Signature checks:** the page's tabs give a URL per check, each its own token, so a checked URL can't be turned into the open one; the open URL keeps working for whoever has it, until the user replaces it (below). GitHub's `X-Hub-Signature-256` and `Authorization: Bearer` use secrets derived per webhook and per check (`try_gh_…`, `try_bearer_…`). Stripe and Linear make their own secret: the user pastes it into the page (from this site's page only, as with a new open URL below: another site's form gets 403), and it's sealed into that URL's token (AES-256-GCM with a key derived from `TRY_SECRET`). It's stored only in that form: the URL is kept as the webhook's checked URL (below) until the link expires. Stripe's `Stripe-Signature` (`t=…,v1=…`, HMAC-SHA256 of `t.body`) must be within 5 minutes; Linear's `Linear-Signature` (hex HMAC-SHA256 of the body) needs a `webhookTimestamp` within a minute.
- **A new open URL:** the open tab's "Get a new URL" (`POST /l/<code>/rotate`) replaces the open URL. Its token then carries the webhook's open-URL generation, kept per webhook in the database (`hooks.open_gen`), and a post or GET to an open URL of any other generation gets 410 (`replaced`), on every instance at once. The webhook ID (the SDK user, so its subscriptions), the link and MCP URL, the history and the checked URLs stay as they were, and the live view gets a line saying the URL changed. Only the link's code can ask (a webhook URL is a different capability, and can't), from this site's page: a request whose `Origin` or `Sec-Fetch-Site` says another site sent it gets 403. Ten an hour per webhook (429 past that).
- **Which URL the agent hears about:** `watch` and `webhook_info` give the checked URL the user last picked (a GitHub or bearer tab they opened, a Stripe or Linear URL they made, or the URL a service last posted to), and say which check it uses. It's kept for as long as the link lives.
- **Limits** (counted in the database, atomically, so they hold across instances; fixed windows: the hour and the UTC day): 60 posts an hour and 500 a day for each of a webhook's URLs (429 with `Retry-After`), so whoever has the open URL can't use up the checked one's. Refused posts (401, 413) don't count; retries do (each is still a request to Wakeshift, so a repeated `Idempotency-Key` can't get round the limits). 1,000 posts an hour from one address to all webhooks, so one sender can't use up the global hour, whatever links it has made (an address is counted as for new links, below: anyone can make links, so the per-URL limits don't bound one sender). 20,000 an hour across all webhooks; once half of that is used, a post to a webhook no agent has used in the last day (no watching conversation, no MCP session seen) is refused as if the hour were over, so a flood to links nobody uses leaves the rest for webhooks agents use. 30 new links an hour per address. An address is an IPv4 address, an IPv6 address by its /64, and an IPv4 address carried in IPv6 (NAT64's `64:ff9b::/96`, IPv4-mapped) as that IPv4 address; its counts are kept as an HMAC of it, for the hour. Why per sending address is safe for services: GitHub sends deliveries from hundreds of addresses, Stripe from about a dozen and Linear from a handful, so even a few shared addresses give thousands of posts an hour across all their users, while each webhook still has its own per-URL limits; `TRY_ADDRESS_PER_HOUR` raises it if a service's addresses ever reach it. `TRY_PER_HOUR`, `TRY_PER_DAY`, `TRY_GLOBAL_PER_HOUR`, `TRY_ADDRESS_PER_HOUR` and `TRY_LINKS_PER_HOUR` change them, and the terms and privacy policy state the limits in use.
- **Overload:** an instance takes 256 requests in flight (posts three quarters of that, so pages and tool calls keep some room) and 900 open streams (live views, MCP GET and listen streams); for one webhook, at most 10 live views and, apart, 10 agents' streams, so agents can't leave the page without one; 2 GET streams for one MCP session; for one address (counted as for the limits), 32 requests in flight (429 with `Retry-After` past that) and 48 open streams, so it takes several addresses to fill an instance (a live view past a stream limit gets 429, a GET stream 405, a listen stream 429). The address is the one `TRY_PROXY_HOPS` picks from `X-Forwarded-For`, else the socket's; a request with neither (its connection already gone) gets 400 rather than sharing one bucket with every other such request. A request's body must arrive within 10 seconds (else 408 and the connection is closed, freeing its slot), its headers within 15 and the whole request within 20 (Node's `headersTimeout` and `requestTimeout`, checked every 2 seconds); Node applies those only until the request has arrived, so they never cut a live view, an MCP stream or a held tool call. Past the instance's room, and when the database is away or out of connections, it answers 503 with `Retry-After` and a plain message (JSON for webhooks, JSON-RPC for MCP, a page for pages), never a 500. A link's page still comes up when the database is slow, without its history; the live view retries and says so (below). Wakeshift's own 429 or 503 on publish becomes a 503 with `Retry-After` for the poster.
- **The page's live view** is SSE from this server (`/l/<code>/live`): each post (received, refused, rate limited, the URL it came to and whether that verified it, the start of what was posted, and how many watching conversations the publish reached), and each watch and unwatch. Lines are kept in the database (the last 50 per webhook) and reach pages on every instance by `NOTIFY` on the webhook's channel (`try_<hook>`; each instance `LISTEN`s only for webhooks it has a page open for, and replays the recent lines whenever its connection comes back after a drop; it pings that connection every 30 seconds so a silent drop is noticed). A webhook's refused and rate-limited posts get at most 10 lines a minute per instance, so a flood of bad signatures doesn't push real posts out. The rest are counted in memory, and once the minute is over (or the instance stops) each instance adds its count to the webhook's one line for that minute (`skipped`, keyed by webhook and minute): the first count writes it, later ones update it in place and notify it again with the same `seq`, which the page replaces. So the page shows one line a minute with the total across instances ("…and 57 more refused or rate-limited posts in the minute from 2:03 PM weren't listed one by one; each was answered with 401 or 429"), and each instance writes it at most once a minute per webhook. A live view that doesn't keep up with what's written to it is dropped (EventSource reconnects). Each line goes with its `seq` as its SSE ID, and a live view asks for the lines after the newest it has (`?after=<seq>`, or `Last-Event-ID` when EventSource reconnects by itself), so after a gap it shows what happened meanwhile (as far as the last 50 go). When the server refuses it (429, 503), EventSource gives up; the page tries again after 2 seconds, doubling to 30 at most (randomized a little), back to 2 once connected, and at once when the page is looked at again, the network comes back or the status poll gets an answer (`liveConnection` in page.ts). The page shows who called `watch`, "sent to N watching conversations" per post, and whether an agent is connected right now and how (stream, hooks or polling): it polls `/l/<code>/status` every 10 seconds, which asks Wakeshift for `webhook.received`'s status with the webhook's ID (`event.status`, read-only).

## Run it locally

With Docker, the server's `docker-compose.yml` runs it beside the server (the profile `webhooks`; its README's "Try it with your agent"):

```sh
sh deploy/webhooks-env.sh                      # once: .env with fresh keys and secrets
docker compose --profile webhooks up --build   # http://localhost:8380
```

Or with Node: you need the core running, a self-serve test key, and Postgres (`make db`).

```sh
# 1. The core, at http://localhost:8370 (from the repo root).
make run            # or: make dev PUBLIC_URL=http://localhost:8370

# 2. In the console (http://localhost:8370, dev sign-in), Build: register an
#    app. Copy its test key (wst_test_…).

# 3. The SDK, then this app.
(cd sdk/typescript && npm install && npm run build)
cd apps/try && npm install && npm run build
docker compose exec postgres createdb -U postgres try   # once (or any database you like)
WAKESHIFT_KEY=wst_test_… WAKESHIFT_CORE=http://localhost:8370 \
  TRY_SECRET="$(openssl rand -base64 48)" TRY_HOST=127.0.0.1 \
  TRY_DATABASE_URL='postgres://postgres:postgres@localhost:5439/try?sslmode=disable' npm start
```

Open http://localhost:8380, get a link, and run the command its tab for your agent shows. `WAKESHIFT_CORE` must be the core's public URL (`WAKESHIFT_PUBLIC_URL`): app assertions are addressed to it, and unset it's Wakeshift's hosted service. Without `TRY_HOST`, it listens on every interface, so anyone who can reach this machine's port 8380 can get links and post. A fresh `TRY_SECRET` each start ends the links made before; keep one to keep them.

| Variable | |
| --- | --- |
| `WAKESHIFT_KEY` | The app's key: a self-serve test key, or a key made with `cmd/appkey` for the app registered in `WAKESHIFT_APPS` |
| `WAKESHIFT_CORE` | Wakeshift's public URL (default `https://app.wakeshift.ai`, the hosted service) |
| `TRY_CORE_ADDR` | Where requests to Wakeshift go if not `WAKESHIFT_CORE` (in docker compose, `http://server:8370`) |
| `TRY_SECRET` | Signs links; at least 32 random bytes. Changing it ends every link. |
| `TRY_DATABASE_URL` | Postgres for what's kept per webhook; every instance shares it. Migrated at startup (`migrations/`). |
| `TRY_MIGRATE_DATABASE_URL` | Optional: the database's owner, which migrates instead, so `TRY_DATABASE_URL`'s role only reads and writes |
| `TRY_DB_POOL` | Connections per instance (default 3), plus one that LISTENs |
| `PUBLIC_URL` | This server's public URL (default `http://localhost:$PORT`) |
| `PORT` | Default 8380 |
| `TRY_HOST` | The address to listen on (default every interface; `127.0.0.1` for this machine only) |
| `TRY_PROXY_HOPS` | How many proxies in front append to `X-Forwarded-For`; 0 (the default) uses the socket's address. At 0 behind a proxy every visitor shares one address's limits (posts and new links); above 0 with the port reachable directly, `X-Forwarded-For` can be forged |
| `TRY_PER_HOUR`, `TRY_PER_DAY`, `TRY_GLOBAL_PER_HOUR`, `TRY_ADDRESS_PER_HOUR`, `TRY_LINKS_PER_HOUR` | The limits (defaults 60, 500, 20000, 1000, 30) |
| `WAKESHIFT_POSTHOG_KEY`, `WAKESHIFT_POSTHOG_HOST` | PostHog, for visits to the home page; unset, no analytics |
| `TRY_HOSTED` | `1` only for Wakeshift's own deployment (try.wakeshift.ai): it serves its Terms and Privacy Policy and links them from every page. Unset, it serves and links none |

Link codes and webhook tokens are in URL paths (`/l/…`, `/t/…`, `/in/…`): keep those paths out of a proxy's access logs.

After changing the SDK, rebuild it and run `npm install` here again: `.npmrc` installs it as a copy (so it shares this app's `@modelcontextprotocol/server` and `zod`), not a link.

## Tests

```sh
npm run lint        # tsc --noEmit
npm test            # unit tests (each on its own new database): links, events, signatures, limits, restarts, two instances, overload
make try-test       # from the repo root: all of that, then end to end against a real core
sh scripts/load.sh  # a load test: a core, two instances on one database, links posting, live views, MCP sessions
```

The unit tests need Postgres (`make db`, or `WAKESHIFT_TEST_DATABASE_URL`); each makes its own database and drops it. The end-to-end test (`test/e2e.test.ts`, run by `scripts/e2e.sh`) starts a core with Go's `TestSDKHarness`, runs this server in process, and connects MCP clients as Claude Code (reading the lines stream like Monitor) and Codex (a fake thread whose connector redeems the beacon), then a second instance behind a round-robin balancer, restarted midway.
